Modules
M1Agents & orchestration

An agent is a model in a loop: it plans, calls tools, observes the results, and continues — until the task is done or the loop is capped. The field's hard-won lesson, from Anthropic's work with dozens of customer deployments: the most successful implementations use simple, composable patterns, not complex frameworks. The distinction that matters: workflows — fixed, pre-scripted LLM call chains — beat agents — model-directed loops — whenever the path is predictable. Agents earn their complexity only when the path genuinely varies: research tasks, multi-step troubleshooting, tasks where the next step depends on what was just discovered.

The PM's questions are the load-bearing part: does the task tolerate a wrong tool call, or does one error cascade? What is the loop's worst case — in cost (agents burn tokens), in time (an unbounded loop never ends), in damage (an agent that can act)? Where does the human observe and intervene — and what does the handoff look like mid-task? Transparency is a design requirement: an agent whose steps you can't see is an agent you can't debug, can't evaluate, and can't trust — which makes the "show your work" interface a product feature, not an engineering nicety.

M2Tools, function calling & interfaces

Tools are how a model acts on the world: search, computation, databases, APIs — exposed through function calling, where the model emits a structured request (function name + arguments) and your system executes it and returns the result into context. Tool design is interface design, and the interface is the spec: the agent-computer interface — clear tool names, unambiguous descriptions, strict argument schemas — is the difference between a tool the model uses well and one it misuses. A tool named "get_customer_info" whose description doesn't say which identifiers it accepts will be called with hallucinated identifiers.

The failure modes are product-relevant, not engineering trivia: the model calls the wrong tool (schema ambiguity), hallucinates arguments (validation needed — every call must be validated before execution), or loops on a failing tool (budgets and retry caps required). And least privilege applies to models more than humans: a support agent doesn't hold the refund API until a human approves — because the tool set is the agent's power, and power without gates is a security incident waiting for a prompt injection (RSK 550 M2). Your deliverable: a tool set designed and tested with a real model, with the failure log to prove it.

tool = structured actionthe interface is the specleast privilege + budgets
Problem set

  2. Test the tools with a real model: which calls succeed, which fail, and why — log the failures.
  3. Write the validation spec: what gets checked before each tool call executes.

M3Evals for agentic systems

Single-call evals don't cover agents, because the unit of work is a trajectory — a sequence of tool calls and observations — and quality lives in the path, not just the final answer. Agentic eval design has four tracks. Task-level success: did it complete the task? (The functional test, HumanEval-style, extended to multi-step.) Trajectory quality: did it take a sensible path — or did it waste calls, wander, or attempt dangerous actions even while succeeding? Tool-use accuracy: right tool, right arguments, no loops — measurable and often the earliest signal of trouble. Cost and latency: agentic systems burn tokens; a loop that works but costs 40× a workflow is a product failure, not a success.

Then the red-team layer (RSK 550 extended): agents have attack surface that single calls don't — prompt injection through tool results (a search result that says "ignore your instructions") and goal hijacking via retrieved content. The eval report for an agent is a different genre — trajectory logs, failure-mode taxonomies, cost curves — and it is a growing one; the PM who can design it is scarce. Your deliverable this module is an agentic eval plan with a real run behind it.

evaluate the trajectory, not the answertool-use accuracy is a metricagents burn tokens — cap the loop
Problem set
  1. Design the agentic eval plan for your M1 use case: task-level success cases, trajectory quality rubric, tool-use accuracy metrics, cost caps.
  2. Run it — even a small run (10 tasks) — and write the report: successes, failure modes, cost per task.
  3. Add the agent-specific red-team: injection through tool results and retrieved content.

M4MLOps awareness & staying current

You won't run the ML platform — you'll partner with whoever does — but you need the vocabulary and the questions: model deployment and versioning (which version is live, and can you roll back in minutes?), monitoring (drift signals, cost, latency, error rates — the production eval plan from AIPM 520 wired into operations), retraining cadence and triggers (what event justifies it, and who decides?), and the eval pipeline as part of CI (every candidate model runs the golden set before it can ship). The PM's role in MLOps is the same as everywhere else: define what "good" means, and make the definition enforceable.

And the meta-skill: staying current in a field that turns over quarterly. The loop that works: one primary news source (The Batch), one practitioner you trust (Simon Willison), monthly hands-on time with new model capabilities — and the discipline that compounds: re-run your own evals against new models instead of reading leaderboards. Your portfolio's eval suite is a permanent asset: it prices every future model that ships. That is what "keeping current" means at a professional level — not knowing the latest model name, but knowing what it does to your use case, in your numbers.

  2. Re-run your AI 510 eval suite against a model you haven't tested yet (local or hosted). Report the delta and what it means for your capstone.
  3. Write the deployment questions you'd bring to an MLOps partner: versioning, rollback, monitoring, retraining triggers.
