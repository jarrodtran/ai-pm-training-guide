AI 510 — AI & LLM Literacy

The technology, taught at PM depth: how large language models work and fail, plus the hands-on instruments — prompting, retrieval, APIs, evals — an AI PM uses daily. Six modules, six problem sets, one case memo.

Course objectives
Explain how LLMs work in plain English — training as lossy compression, attention, tokens, context.
Design prompts systematically and build a reusable prompt library.
Build a retrieval-augmented (RAG) product with no-code tools.
Call an LLM API and read a small Python script.
Measure model quality with an eval suite — and write a case memo.
Modules
M1The Transformer: how LLMs work

A language model is a statistical machine trained to predict the next token — a word fragment — given everything before it. That sentence is the entire technical foundation of this program; everything else is consequences. Training is the expensive process: the model reads internet-scale text and adjusts billions of parameters so its predictions get better, which is best understood as lossy compression — the model absorbs patterns, not the text itself. It "knows" the statistical shape of the world's writing; it does not store a database of facts. This single idea explains both the capability (fluent, knowledgeable-sounding generation) and the failure (hallucination: patterns confidently mis-assembled into falsehood).

Attention is the mechanism that lets each token weigh the relevance of every other token in the context — it is what makes long-range meaning possible, and it is the reason the 2017 transformer paper (Attention Is All You Need) changed the field: attention-only architecture, no recurrence, massively parallel. Inference is the cheap operation you pay for per token: feed tokens in, sample the next, repeat until done. Two properties follow and will recur all program: capability is not reliability (what it can do in a demo is not what it will do in production), and the context window is the model's only working memory — what is not in context does not exist for it.

training = lossy compressioncapability ≠ reliabilitycontext window = working memory

M2Tokens, context & inference

Tokens are the unit the model reads and writes — roughly word fragments, but irregular: "unbelievable" might be two tokens, and 100 words is roughly 130–140 tokens depending on language and vocabulary. Tokens matter to a PM because everything is priced and constrained in them: the context window, the bill, and latency all scale with token counts. Get fluent at estimating: a page of text ≈ 500 words ≈ ~650 tokens.

Temperature is the randomness knob: low values make output deterministic and repetitive; high values make it creative and erratic. Products that need consistency (extraction, classification, structured data) run low temperatures — but note that temperature 0 is not a guarantee of identical outputs, only of high probability. Hallucination is the load-bearing failure: it is not a bug to be "fixed" out of existence but a property to design around — via retrieval (M4), evals (M6), guardrails, and human-in-the-loop. The professional stance: treat every model output as plausible until verified, and design the product so that verification is cheap.

tokens = the currencyhallucination = property, not bugtemperature = determinism knob
Problem set
  1. Paste three different inputs (a paragraph, a support ticket, a contract clause) into a tokenizer or the API and record token counts; build an intuition for words→tokens.
  2. Run the same prompt at temperature 0, 0.7, and 1.2 — note what changes and what doesn't.
  3. Draft the outline of your "AI 101" explainer (deliverable): the five ideas a non-technical reader must walk away with.
Seminar
  • Which product decisions require determinism, and which are fine with variation? What does that imply for temperature by use case?
  • If a customer complains the bot "made something up," what does the AI PM actually owe them — an apology, a fix, or an explanation of the property?
Self-check
  • ☐ I can estimate token counts for typical inputs
  • ☐ I can explain temperature and when to lower it
  • ☐ I can explain why hallucination is designed around, not "fixed"

M3Prompting as an interface

The prompt is the product's interface to the model — which makes prompt design interface design. The core pattern: role (who the model is: "you are a senior support agent for X"), context (the situation and constraints), task (what to do), and format (how to output). Add few-shot examples when behavior matters more than prose — two or three worked examples beat a paragraph of instruction — and structured output (JSON with a schema) whenever a machine consumes the result. Serious products force structure; free prose is for chat, not for pipelines.

Two deeper truths. First, prompt engineering shifts behavior; it does not rebuild the model. When a prompt grows past a page, you are fighting the model — the design, not the prompt, is the problem. Second, prompts are attack surface: the model follows instructions it finds anywhere in its input, including user-supplied text — the security hole called prompt injection (full treatment in RSK 550; for now, know it exists and that your prompts are not a wall). Version your prompts, test them, and measure them like any interface.

role · context · task · formatfew-shot beats prosestructured output for pipelines
Problem set
  1. The 20-prompt challenge: pick one high-value use case (client status updates, vendor proposal summaries, FDE scoping questions). Build 20 prompts testing variations: role/context/task/format, few-shot vs. no-shot, "ask clarifying questions first," structured output.
  2. For each prompt, record: the prompt, why it works, and one bad variant with its failure mode.
  3. Save the 15 best as your prompt library (prompts/).
Seminar
  • Where does prompt engineering end and product design begin? What's the smell that a team is prompting its way around a design gap?
  • What breaks first when a prompt library grows to 200 prompts?

M4Retrieval & no-code building (RAG)

A model's parameters are its trained knowledge — frozen at training time, unreliable for your documents. Retrieval-augmented generation gives the model a working memory: chunk your documents, convert each chunk into an embedding (a vector where similar meanings sit nearby), store them in a vector index, and at query time fetch the most relevant chunks into the context window. The model then answers from what is in front of it — which is why RAG reduces hallucination and keeps answers current: update the documents and the answers update. The Lewis et al. 2020 paper that named the pattern frames it as parametric memory (the model) plus non-parametric memory (the retrieval index).

The architecture you must be able to draw from memory: documents → chunking → embeddings → vector store → (query → retrieve top-k → stuff into context) → model → grounded answer. The failure modes are measurable and yours to own: bad retrieval (the right chunk didn't make top-k), bad chunking (the answer straddled two chunks), and Lost in the Middle — the Liu et al. 2023 finding that models use information at the ends of long contexts far better than the middle, which means where you place retrieved content is a design decision, not a detail. Retrieval quality is product quality.

parametric vs. non-parametric memorygrounding beats improvisationretrieval quality = product quality
Problem set
  1. Build a document-Q&A bot with a free-tier builder (Claude/Google AI Studio projects, Flowise, or n8n). Upload 3–5 real documents.
  2. Test 25 questions across difficulty levels; record pass/fail and the failure cases.
  3. Write the 1-page architecture write-up: draw the pipeline, note where retrieval, context, and generation sit, and diagnose three failures with hypotheses about why they failed.
Seminar

  • What happens to a RAG system when the source documents contain contradictions? How would you detect it?

M5Python & the API layer

Why does an AI PM learn Python? Not to ship production code — to verify, evaluate, and estimate. Three recurring uses: run evaluation scripts that score model outputs; read the code engineers and data scientists write well enough to ask good questions; and build prototypes that test feasibility before anyone commits engineering time. You are not becoming a developer; you are becoming fluent enough to be dangerous in meetings and honest in estimates.

The pattern to internalize: an endpoint is a URL that accepts a request (your prompt + parameters, authenticated by an API key) and returns a response (the model's output plus usage — tokens in and out). Cost flows from usage: price per million input tokens plus price per million output tokens (output typically costs 3–5× input — always check current pricing). Your first script: prompt → response → print token usage. Your second: a chain — call one summarizes, call two extracts bullet points, call three grades them. That three-call chain is the seed of every agent architecture you will ever discuss. Use Google Colab for zero setup, or Ollama locally for zero cost.

endpoint · request · response · keytokens in/out = costchains seed agents
Problem set
  1. Make the call: Ollama (free) or ~$5 of hosted credits (OpenAI/Anthropic). Script 1: prompt → response → usage.
  2. Script 2: the 3-call chain (summarize → bullets → grade).
  3. Comment every line yourself — the commenting is the learning.
  4. Write the API README: endpoint, key, request/response, token, rough cost of one call.
Seminar
  • What should a PM never use code for — where does the boundary sit between "verify with a script" and "build the product"?
  • When a teammate says "it's a simple API integration," what do you now know to ask?

M6Measurement: evals & metrics · Case A: GitHub Copilot

The accuracy trap: a model that answers "yes" to everything scores 90% "accuracy" on skewed data while being useless. The discipline of evals exists to defeat this. An eval set is a fixed collection of cases with expected behaviors; a run scores the model against it. For classification: precision = of the things the model flagged, how many were right; recall = of the things that should have been flagged, how many it caught. They trade off, and your threshold is a product decision — medical screening wants recall; spam filtering wants precision. For generative output, scoring is fuzzier: rubric-based human review, LLM-as-judge (fast and cheap, but biased — spot-check it against humans), or functional tests — the HumanEval insight from Chen et al. 2021, where code is graded by whether it passes tests (Codex solved 28.8% on first sample; 70.2% with 100 samples — the birth of evaluation-by-execution).

The Copilot case (case packet A) is the meta-lesson: when the artifact is open-ended — code, prose, plans — measurement is a design problem. GitHub's controlled experiment found 55% faster task completion (n=95, P=.0017); an independent field study later found no significant effect on weekly activity; and "share of code written by AI" is an input metric, not an outcome. The PM who defines the metric system controls the strategy conversation — this module is where you start owning that.

accuracy trapprecision vs. recallgolden setsmeasurement = design problem
Problem set
  1. Build an eval suite for your M4 bot: 25 cases (easy, edge, adversarial, out-of-scope) with expected behaviors.
  2. Run it, score it, find the failure patterns. Fix the worst pattern (document, instructions, retrieval). Re-run. Record before/after.
  3. Read case packet A. Write case memo 1 (1 page): how you would measure Copilot's value — north star, guardrails, which vendor claims you'd trust and which you'd discount.
