4.1 Version control mental model

  • Repository: The project’s history and files as a database of snapshots.
  • Commit: An immutable snapshot with parent(s) — a node in a DAG (directed acyclic graph) of history.
  • Branch: A movable pointer to a commit — a line of work, not a copy of the world.
  • Why PMs care: Parallel work, auditability, release identity, and rollback all come from this model — not from “files on a shared drive.”

Branching strategies

Strategy Shape PM implications
Trunk-based Short-lived branches; integrate to main often Faster feedback; needs solid CI and feature flags
GitFlow Long-lived develop/release/hotfix Heavier ceremony; longer merge risk; still widely referenced
Env branches (dev/stage/prod) Branch ≈ environment Easy to misuse as permanent forks; prefer promote artifacts, not long-lived env branches

4.2 GitHub in practice

Pull requests

A PR is simultaneously: peer review surface, audit trail, and quality gate. CI checks (lint, tests, build) are automated votes — red means “not ready,” not “engineers being difficult.”

Google eng-practices: small changes, clear *why* in description — your unblock lever is clarifying requirements/acceptance, not reviewing diffs as a coder.

Issues, epics, boards

  • Issue: Unit of tracked work; labels encode type/risk/client.
  • Epic: Theme spanning issues — map to outcomes, not a junk drawer.
  • DoD (Definition of Done): Must include tests/docs/observability *and* your acceptance criteria for client-facing work.
  • Boards show state; they do not create priority — you do.

Conflicts, rebase, cherry-pick, rollback (what they *mean*)

Phrase Mechanical meaning What you do
Merge conflict Two histories edited the same region; human must choose Don’t panic-schedule; ask which intent wins; unblock with product priority
Rebase Replay commits onto a new base for linear history Coordination cost; freeze conflicting work if needed
Cherry-pick Copy one commit onto another branch Hotfix path — confirm it doesn’t skip needed dependencies
Rollback / revert Undo a release or commit in history-preserving way Product decision on user impact; communicate

4.3 The PM’s GitHub cockpit

Look at Why Do not
PR list aging / review latency Unblock reviews; spot stuck work Nitpick code style
CI red on release candidates Release readiness Re-run blindly without asking what’s failing
Issue labels + burndown vs acceptance Outcome progress Equate ticket count with value
Linked ADR / SOW / acceptance in PR description Traceability Require yourself as code approver
Release notes / tags What actually shipped Micromanage commit messages

Velocity without micromanagement: Time-to-first-deploy, reuse rate, lead time for changes (DORA), open PR age, escaped defects — not lines of code.

Folded AI-PM note: Model/prompt/retrieval changes need the same regression gates as code — your eval suite is part of DoD (M4).
