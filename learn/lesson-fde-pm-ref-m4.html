4.1 Version control mental model

From Pro Git / GitHub About Git / What is Git:

  • Repository: History + files as a database of snapshots
  • Commit: Immutable snapshot with parent(s) — a node in a DAG of history
  • Branch: Movable pointer to a commit — a line of work (Branches in a Nutshell)
  • Why PMs care: parallel work, auditability, release identity, rollback — not “files on a shared drive”

Branching strategies

Strategy Shape PM implications
Trunk-based Short-lived branches; integrate to main often Fast feedback; needs solid CI + feature toggles
GitHub Flow Branch → PR → main; simple Good default for many product teams
GitFlow Long-lived develop/release/hotfix Heavier ceremony; longer merge risk (contrast, not prescription)
Env branches (dev/stage/prod) Branch ≈ environment Easy to misuse as permanent forks; prefer promoting artifacts

Ship without long-lived forks: Feature toggles (Fowler) and Branch by Abstraction let you integrate continuously while hiding incomplete work — critical when FDEs would otherwise open client-specific eternal branches.

4.2 GitHub ecosystem in practice

Pull requests

A PR is peer review + audit trail + quality gate. CI checks (lint, tests, build) are automated votes — red means not ready (GitHub Actions / CI; Fowler Continuous Integration; Continuous Delivery).

Merge strategies (GitHub about merges): merge commit vs squash vs rebase — different history shapes; ask which your team standardizes and why (audit vs cleanliness).

Google eng-practices: small changes; clear *why* in description. Your unblock lever is clarifying requirements/acceptance — not reviewing diffs as a coder. Reviewer guide: what healthy review optimizes for (design, readability, simplicity).

Issues, epics, boards

  • Issue: tracked work unit; labels encode type/risk/client
  • Epic: theme spanning issues — map to outcomes
  • DoD: tests/docs/observability and your acceptance criteria for client-facing work
  • Boards show state; they do not create priority

Conflicts, rebase, cherry-pick, rollback

Phrase Meaning What you do
Merge conflict Two histories edited same region Ask which *intent* wins; unblock with product priority
Rebase Replay commits onto new base Coordination cost; freeze conflicting streams if needed
Cherry-pick Copy one commit onto another line Hotfix path — confirm dependencies aren’t skipped
Rollback / revert Undo release/commit preserving history Product call on user impact; communicate

4.3 The PM’s GitHub cockpit

Look at Why Do not
PR age / review latency Unblock reviews Nitpick style
CI red on release candidates Release readiness Blind re-runs
Issues vs acceptance outcomes Progress to “done” Equate ticket count with value
ADR/SOW/acceptance linked in PR Traceability Make yourself code approver
Tags / releases What shipped Micromanage commit messages

Velocity without micromanagement: time-to-first-deploy, reuse rate, DORA lead time, open PR age, escaped defects — not lines of code.

Folded M4: Model/prompt/retrieval changes need the same regression gates as code — eval suite is part of DoD.
