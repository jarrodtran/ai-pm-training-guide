2.0 Why literacy matters for an FDE-PM

Without shared vocabulary you cannot:

  • Spot a one-way door disguised as a “quick” choice
  • Challenge a hand-wavy design without becoming the engineer
  • Translate security/architecture review into SOW language
  • Know when “we need two more weeks” is uncertainty vs scope growth

2.1 Core architectural concepts

Client-server, monolith, microservices, distributed systems

Shape Strength Cost you must price
Monolith Simple deploy; easy local reasoning Change collision; scaling one hot path scales all
Microservices Independent deploy *if* domains are bounded Network failure modes; ops overhead; distributed transactions
Distributed system Scale and isolation Partial failure is normal → SLOs, retries, idempotency

Monolith first (Fowler) is often rational. Microservices are a *premium* paid for independent teams/releases — not a maturity badge. Unbounded service graphs become unownable (Conway; Uber domain architecture). Demand bounded contexts.

C4 model: Force shared altitude — context vs container vs component — in every architecture conversation.

Sync vs async execution

Style Mechanisms PM implications
Synchronous REST/HTTP request-response User waits; latency budget is product; timeouts are UX; HTTP status semantics matter (RFC 9110, MDN HTTP)
Asynchronous Webhooks, Kafka/RabbitMQ event streams Eventual consistency; “done” means *processed*, not *acknowledged*
Broker patterns Routing, transformation, dead-letter, competing consumers (EIP) Failure handling is a requirement: who retries, who alerts, what the user sees

When an engineer says “the REST call failed,” decode with HTTP semantics: 4xx (client/contract), 5xx (server), timeouts (budget), 429 (rate limit — UX policy required).

CAP and distributed trade-offs

CAP (Brewer; “twelve years later” InfoQ): in a partition, you trade consistency vs availability. You do not “pick all three” under partition. For PMs: when a client demands “always up” *and* “always perfectly consistent across regions,” you are being asked to deny physics — reframe as SLO + conflict policy.

Data persistence

Store Use when PM traps
SQL / relational Strong consistency, joins, audit (PostgreSQL concepts) Schema evolution is a one-way door — migrations belong in change control
Document / NoSQL Flexible documents, certain scale patterns (MongoDB document model) “Schemaless” still has an implicit schema; query patterns lock you in
Cache (Redis) Latency lever Stale reads are a product decision; TTLs affect acceptance
Warehouse Analytics Never put the assistant’s hot path on the warehouse

**Kleppmann (*Designing Data-Intensive Applications*)** remains the credibility text for serious data conversations.

AI overlay (folded M1–M3)

  • Transformer / context budget: finite window; middle degrades (Lost in the Middle)
  • RAG: retrieve → condition → generate — still the enterprise assistant default
  • Agents: reason + act (ReAct); prefer simple composable patterns (Anthropic — Building effective agents)
  • Prompting ≠ training (few-shot is in-window pattern completion)

Failure isolation patterns

Circuit breaker (Fowler): stop calling a sick dependency so the whole system doesn’t melt. PM ask: what does the user see in open-circuit mode? Fail open vs fail closed is a product/safety choice.

Distributed-systems pattern map (Fowler patterns article): shared vocabulary for what your FDE means by “we need a saga,” “outbox,” “idempotent consumer.”

2.2 Reliability, networking & security

Performance vocabulary

  • Latency budget: End-to-end time allocated across retrieval, model, tools, network
  • Throughput: Successful work per unit time
  • Concurrency: In-flight work saturating pools and limits
  • Rate limiting: Protects systems; product must define degraded UX
  • Tail latency: p99 hurts more than averages (Dean & Barroso — Tail at Scale)
  • SLOs: Negotiated reliability budgets (Google SRE), not vibes
  • Overload / risk (SRE handling overload; embracing risk): error budgets are how you negotiate features vs reliability without endless argument

Security lexicon (decision altitude)

Term Meaning for the PM
CIA triad Confidentiality, Integrity, Availability — map design reviews here
RBAC / ABAC Role vs attribute entitlements; retrieval must respect the *requesting user* (NIST SP 800-162)
OAuth 2.0 / OIDC Delegated auth / modern identity layer
SAML / SSO Enterprise federation — often a commit-blocker
VPC / peering Network boundaries; air-gap and private connectivity are one-way doors
Zero Trust (SP 800-207) Never trust network location alone

Enterprise trust (folded M8): Map OWASP LLM Top 10 and NIST AI RMF (govern / map / measure / manage) to design decisions *before* security review. Questionnaire answers come from architecture, not “ask eng later.”

2.3 Technical debt & engineering overhead

Technical debt (Fowler Technical Debt Quadrant): deferred cost with interest — reckless/prudent × deliberate/inadvertent. Not “engineers want to polish.”

Toil (SRE): manual, repetitive, automatable work that creates no enduring value. High toil on an FDE team is a productization signal.

Negotiation Bad PM move Better move
Refactor vs feature “No refactors until roadmap done” Price interest (slow delivery, incidents); schedule paydown as capacity %
Platform vs bespoke Always yes to client Config / priced bespoke / product candidate
Utilization 100% billable Dual allocation: deploy / harvest / core
