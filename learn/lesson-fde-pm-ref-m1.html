1.0 How to read this chapter

Enterprise FDE work fails less often from “wrong architecture” than from wrong problem, wrong instrument, or wrong contract. This chapter is the operating system for those three decisions. Everything later (SWE lexicon, FDE model, GitHub cockpit) is vocabulary and mechanism in service of this.

1.1 The core PM mandate: outcomes into scope without dictating “how”

What “good” looks like

A strong FDE-PM turns a customer business outcome into an engineering scope that has:

  1. 1. A measurable definition of success (baseline → target → measurement source)
  2. 2. Explicit constraints (data, identity, residency, latency, compliance)
  3. 3. Explicit non-goals (what you will *not* build this engagement)
  4. 4. Clear ownership boundaries (you / FDE / client / security)
  5. 5. Acceptance criteria agreed before build (folded M4)

You do not specify algorithms, schemas, or frameworks unless they are true one-way doors the business is buying (e.g., “must run air-gapped,” “must use customer IdP”).

SVPG frame: four big risks (discovery, not delivery theater)

Before you fund a solution, force the work through four risks (SVPG — four big risks):

Risk Question FDE-field tell
Value Will customers/users choose to use this? Shadow shows workarounds; “AI” is status, not job-to-be-done
Usability Can they figure it out in their workflow? Ticket UI / spreadsheet is the real UI
Feasibility Can we build it with the people/tech we have? Air-gap, dirty data, no API, no SSO
Viability Does it work for the business (margin, risk, support)? Bespoke forever destroys margin (S-1-shaped risk)

Continuous discovery (SVPG product discovery) is not a workshop you run once before a SOW. It is a habit: every engagement produces evidence that updates the opportunity, not just tickets that update a board. If your calendar is 100% delivery coordination, you are in delivery theater — related to product-management theater (title says PM; job is backlog/coordination).

Opportunity assessment before solutions: write the opportunity as who struggles, what they do today, what “better” means in a number, and why now — *then* entertain instruments. Solution-first discovery is how you buy a model for a SQL join problem.

Empowered vs feature/delivery teams: When you lead FDEs, the gravitational pull is “build what the client asked.” Empowered product work means your team owns outcomes and says no (with a price). Feature/delivery mode means your team is a high-cost implementation arm.

Working Backwards / PR·FAQ (enterprise cousin of the PRD)

Amazon’s Working Backwards discipline (About Amazon culture/process; Vogels — Working Backwards) is useful even outside Amazon: start from the customer-facing narrative of the finished capability, then force the hard questions early.

A practical PR/FAQ (or equivalent brief) for FDE engagements:

  • Press release: What did the client’s operator gain, in plain language?
  • FAQ — customer: Who uses it? What replaces what? What happens when it’s wrong?
  • FAQ — internal: What data do we need? What is out of scope? What is the run-rate cost? What is the acceptance bar?

This does not replace a SOW. It prevents a SOW that is only a feature list.

Folded M0 — your seat

  • Dev vs Delta: Deployment context defines the FDE. You own missing *product* decisions.
  • PM ≠ project management: Sequencing is not strategy.
  • Exit PM-theater.
  • Instruments: numbered problem, ADR expectations, acceptance, priced triage, pattern ledger / productization memo.

Worked example: Stakeholder wants to “fine-tune so the bot remembers our 200-page policy.” You reframe the *decision*: retrieval + faithfulness acceptance, not memorize-via-train. FDE builds retrieval. You own the bar and the “no” to fine-tune-as-memory.

1.2 PRD vs technical spec vs SOW

These artifacts answer different questions. Collapsing them is how disputes appear at the fragile moment (pilot acceptance, change orders, “but the demo worked”).

Artifact Primary author Core question External guarantee?
PRD / product brief / PR·FAQ PM Why, who, success metrics, non-goals, UX intent No — intent
Technical spec / design doc FDE / Tech Lead How, components, interfaces, failure modes Internal builder agreement
SOW PM (+ legal/sales) In/out, access, acceptance, change control, commercial terms Yes — external commitment
Discovery RFC PM + FDE lead What we learned; instrument choice; risks; proposed SOW shape Pre-commit alignment
ADR FDE drafts; PM owns decision One durable choice + consequences Decision record, not a schedule

Analytical rules

  1. 1. Ambiguity in a SOW is not flexibility. It is dispute inventory timed for when trust is thinnest.
  2. 2. Demo illusion. Demos are arranged to look excellent. Defense: pre-agreed thresholds on a client-authored golden set.
  3. 3. Expectation math. If acceptance is undefined, every stakeholder will invent a different “done.”
  4. 4. C4 altitude. In reviews, demand the right diagram level (context / container / component) so you are not arguing UI while they mean network.
  5. 5. API house style. When negotiating interfaces, Google API Design Guide is a shared reference for resource naming, errors, and versioning intent — you are negotiating a long-lived contract (see also Stripe versioning in Module 3).
  6. 6. Fifth-stakeholder discipline. Procurement, legal, security, data governance, IT ops: bring them into discovery as informed participants, not late vetoes.

1.3 Enterprise discovery & scoping (constraints before commit)

Ask ≠ problem

“We want an AI assistant” is a request. Behind it is a process, a queue, a cost, a person’s week. Practice: never leave discovery without a sentence containing a number and a name (“claims intake spends 14 hours/week re-keying faxes; Maria owns that queue”).

Three diagnoses (first meeting) — folded M6

Diagnosis Signals Correct response
AI problem Unstructured input; fuzzy judgment; high volume + ambiguity Retrieval + model + eval before build
Deterministic pipeline Structured rules; exactness required (money, eligibility, safety) Connectors, CDC, transforms — no model in the exact decision path
Change-management failure Tool exists; adoption is the issue No new system — sponsorship, process, incentives (Kotter anatomy)

Most enterprise “AI projects” are two of three stacked. Name and price each layer separately.

JTBD and shadowing

Jobs to be Done: the real job is often a spreadsheet or chat workaround, not the official SOP. Shadow the work. The gap between documented process and real process is where integration complexity *and* adoption risk live.

Constraint hunt (commit-blockers)

Domain What to uncover before commit Why it kills pilots late
Legacy / integration Source of truth; batch vs real-time; undocumented APIs Scope explodes in week three
Compliance / residency / air-gap What may leave the estate Security veto after demo
Latency / throughput SLA language; peak load “Too slow” with no budget
Identity SSO/SAML/OIDC; entitlement model Retrieval without ACL = non-starter
Data quality Completeness, duplication, label noise Model blamed for data sins

Climb buy → adapt → build

Configure an existing product; extend; integrate; only then build. Building is justified when the pattern is core differentiation, nothing credible exists, or integration cost dominates — not because it is more fun.

Artifacts path: Discovery workshop → Discovery RFC → feasibility → SOW. Instrument triage on the whiteboard.

1.4 Backlog health: customization vs platform generalization

Pressure If unmanaged PM counter
Client one-offs Permanent forks; margin death Price: config / bespoke displacing X / product candidate
Utilization as north star Harvest starved Dual clocks: client dates vs product quarters
“Just this once” Scope-creep tax 3-day triage; SOW change control
Third identical ask Still bespoke Three-client rule → pattern ledger + productization memo

Reuse rate (with quality and satisfaction guardrails) beats utilization as the team KPI. Bespoke is inventory with carrying cost — legitimate for logos and learning, expensive if never harvested (folded M9–M11).
